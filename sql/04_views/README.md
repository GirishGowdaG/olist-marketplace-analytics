# sql/04_views — Analytical Views Powering Power BI

Three `CREATE OR REPLACE VIEW` scripts that materialise complex multi-table aggregations into clean, single-table views. These views feed the Power BI dashboard directly via Import Mode, replacing complex DAX with precomputed SQL that is testable, version-controlled, and readable.

| File | View Name | Feeds | What It Computes |
|---|---|---|---|
| `01_cohort_retention_matrix.sql` | `cohort_retention_matrix` | Customer Retention page (cohort heatmap) | For each acquisition cohort × month offset: active customer count + retention % |
| `02_payments_by_state.sql` | `payments_by_state` | Payments & Affordability page | Credit card %, boleto %, voucher %, avg installments, avg order value — per state |
| `03_review_reason_summary.sql` | *(documentation only)* | Voice of Customer page | This table is generated by `python/reason_analysis_v2.py`, not a SQL query — this file documents its schema for reference |

## Why Views Instead of CTEs in Power BI?

Power BI can execute CTEs in a native SQL query. So why create permanent views?

**Two specific technical failures forced this decision:**

1. **Cross-filter contamination on the cohort retention measure.** A DAX measure computing retention % was leaking filter context through the `fact_order_items ↔ fact_reviews` relationship — clicking a category bar inflated the retention percentage past 100%. Moving the cohort aggregation into a precomputed SQL view removed the measure from the problematic relationship graph entirely.

2. **Many-to-many leakage on the payments pivot.** The conditional aggregation across 27 states required a `TREATAS()` join in DAX because the relationship engine couldn't safely route filters. After two rounds of DAX debugging, precomputing the pivot in SQL was the correct engineering trade-off: more debuggable, faster to load, and the query is now readable by anyone.

**General principle:** when a DAX fix requires more debugging than the insight it supports is worth, the complexity belongs in SQL. Views are the correct abstraction layer between a complex database and a BI tool.

## `01_cohort_retention_matrix.sql`

**Logic:** Four-stage CTE.
1. `customer_cohort` — each customer's first order month (`customer_unique_id` not `customer_id`)
2. `customer_orders` — all active months per customer, deduplicated to one row per (customer, month)
3. `cohort_data` — join cohorts to all activity, compute month offset with `PERIOD_DIFF`
4. `cohort_sizes` — cohort size at month 0 (the denominator for retention %)

Final `SELECT` produces one row per (cohort_month, month_offset) with active_customers, cohort_size, and retention_pct. Power BI reads this as a flat table and renders it as a heatmap using conditional formatting.

**Why `PERIOD_DIFF` and not `DATEDIFF`?**
`DATEDIFF` returns the number of days between two dates. For cohort analysis you need the number of *months* between two month-year values, regardless of exact day. `PERIOD_DIFF` on `EXTRACT(YEAR_MONTH ...)` converts both dates to YYYYMM integers and subtracts them — producing an exact month count with no rounding or partial-month errors.

## `02_payments_by_state.sql`

**Logic:** Two-stage CTE.
1. Joins orders, customers, and payments — one row per order with state + payment details
2. Pivots payment types into columns using conditional aggregation: `SUM(CASE WHEN payment_type = 'boleto' THEN 1 ELSE 0 END)`

**Note on percentages:** Payment percentages do not sum to exactly 100% because one order can have multiple payment rows (split payments — partial credit card + voucher). This is correct behaviour reflecting the source data model, not a calculation error. The column values store raw ratios (0.286, not 28.6) so Power BI's native percentage format handles display everywhere without per-visual hacks.

## `03_review_reason_summary.sql`

This file documents the schema of the `review_reason_summary` table for SQL-layer reference. The table is created and populated by `python/reason_analysis_v2.py`. It was not implemented as a SQL view because the source data (classified reason tags per review) is generated by the Python rule-based classifier — there is no SQL query that could produce it.

Schema:
```sql
review_reason_summary (
    sentiment_label  VARCHAR(10),
    reason           VARCHAR(60),
    review_count     INT,
    pct_of_sentiment DECIMAL(5,1),
    PRIMARY KEY (sentiment_label, reason)
)
```

Power BI reads this as a flat table. The Voice of Customer page renders it as grouped bar charts (reason × sentiment) after filtering to the relevant sentiment label on each visual.
