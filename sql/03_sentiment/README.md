# sql/03_sentiment — NLP Output Schema

One file. One table. This is the bridge between the Python NLP pipeline and the SQL analytical layer.

## File

| File | Purpose |
|---|---|
| `01_create_review_sentiment.sql` | Creates the `review_sentiment` table using `CREATE TABLE IF NOT EXISTS` — idempotent, safe to run multiple times |

---

## Table Schema

```sql
review_sentiment (
    review_id       VARCHAR(50)  PRIMARY KEY,
    order_id        VARCHAR(50)  NOT NULL,
    sentiment_label VARCHAR(10)  NOT NULL,   -- 'positive' / 'neutral' / 'negative'
    sentiment_score DECIMAL(5,4) NOT NULL,   -- model confidence (0.0000 – 1.0000)
    model_name      VARCHAR(80)  NOT NULL,   -- which model produced this score
    scored_at       DATETIME     NOT NULL,   -- run timestamp for auditability
    INDEX idx_order  (order_id),
    INDEX idx_label  (sentiment_label)
)
```

---

## Design Decisions

**Why store `sentiment_score` (model confidence)?**
The BerTweet-PT model was trained on tweets, not product reviews — there is inherent domain shift. Low-confidence predictions are more likely to be wrong. Storing the raw confidence score per review means downstream analysis can filter to high-confidence labels only (e.g., `WHERE sentiment_score > 0.80`) rather than treating every prediction as equally reliable.

**Why store `model_name`?**
If the model is upgraded or replaced in a future run, the table records which version produced each score. This is standard MLOps practice for any scored output that will be used in business decisions.

**Why `CREATE TABLE IF NOT EXISTS` and not `DROP TABLE`?**
The Python pipeline in `sentiment_analysis.py` is designed to be resumable: if the scoring run is interrupted after 20,000 reviews, re-running it skips already-scored reviews via `NOT IN (SELECT review_id FROM review_sentiment)`. Dropping and recreating the table on each run would destroy that resumability.

**Why a separate table and not a column added to `order_reviews`?**
The NLP pipeline runs after the base data is loaded. Adding a column to `order_reviews` would require an `ALTER TABLE` that modifies the source data layer. Keeping sentiment in a separate table follows the analytical engineering principle of never modifying your source tables — you extend by adding, not by mutating.

**`review_reason_summary` table** (documented here, generated by Python)
A second NLP-output table — `review_reason_summary` — is generated by `python/reason_analysis_v2.py` and documented in `sql/04_views/03_review_reason_summary.sql`. It aggregates reason-classification counts by sentiment and feeds the Voice of Customer dashboard page directly.
